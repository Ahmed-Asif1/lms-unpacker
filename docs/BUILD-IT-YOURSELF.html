01 / PRODUCT

The problem is repeated small decisions.

An LMS download may contain ten layers of wrappers around a handful of lectures. Another course may use week names, while Calculus just has “Continuity.pdf.” People need quick extraction today and repeatable organization over a semester. The app gives these jobs a shared engine, with optional organization rather than a mandatory course setup.

Flatten

Take each file’s final name and put it beside the ZIP. Good for wrapper-heavy course downloads.

section/resources/Lecture.pdf → Lecture.pdf

Just unzip

Preserve the archive hierarchy inside a folder named after the ZIP. Useful when relative links or project folders matter.

notes.zip → notes/section/Lecture.pdf

Organize

Optionally route by course, category, week or topic. Rules use filenames and explicit syllabus mappings.

Continuity.pdf → Lectures/Limits and continuity/

Five promises shape the implementation

  1. Offline operation. Materials stay on the computer. No account, document upload or online inference is part of extraction.
  2. Preview before GUI Apply. The user sees destinations and conflicts. Editing relevant choices makes the old preview invalid.
  3. Simple distribution. One desktop EXE, one independent Windows CLI EXE, or one independent Linux shell file. A single download does not mean the source has to be one huge file.
  4. Honest organization. A filename without a reliable week stays Unscheduled unless the profile supplies one. Broad topics can use explicit week ranges.
  5. Clear defaults. Flatten, skip existing names and permanently delete successfully processed ZIPs, including intentionally skipped incoming files.
Deletion is a product decision, not a cleanup accident.Skip preserves the existing destination. It does not preserve a different incoming version if the ZIP is deleted. Keep ZIP and Rename are available because those are different intentions. Errors retain the affected archive. These distinctions must survive a rewrite.

Start with three concrete examples

For section/lecture.pdf, Flatten produces lecture.pdf. For a website containing index.html and images/plot.png, Extract preserves the relative folder layout. For an explicit course rule matching *continuity*, Organize can place that lecture into a named topic or a scheduled week. These are three destinations, not three separate extraction implementations.

02 / TOOLS

A small stack built on the operating system.

PowerShell handles file operations and orchestration. WPF supplies the Windows interface. Two small C# pieces handle byte-oriented integrity checks and the single-file executable wrapper. The HTML guides use ordinary HTML, CSS and JavaScript.

A few PowerShell patterns you will see everywhere

# A hashtable: named options, like a small dictionary.
$options = @{ Path='C:\Courses'; Mode='Flatten'; KeepZip=$false }

# Splatting: pass each key as a named parameter.
$result = Invoke-LmsUnpacker @options -Preview $true

# A structured result rather than a sentence to parse.
[pscustomobject]@{ Written=1; Skipped=0; Errors=0 }

# LiteralPath treats brackets and wildcard characters as filename text.
Get-Item -LiteralPath $path

# finally runs even after an error: file handles must not leak.
try { $stream = $entry.Open(); # Read from $stream here.
} finally { if ($stream) { $stream.Dispose() } }

The last fragment illustrates cleanup structure; the real reader consumes chunks from the stream inside the try block. A .ps1 is an executable script; a .psm1 is a module with an explicit export boundary. Dot-sourcing a script executes it in the caller’s scope, which is why desktop helpers can use the same $ui dictionary.

04 / WALKTHROUGH

Follow one ZIP from selection to completion.

Imagine selecting Courses/Calculus/download.zip, containing Week 02/Continuity.pdf. Use Flatten, Skip, and the default Delete ZIP choice.

Discover the filename

A separate discovery worker lists ZIP paths in the chosen scope. It has not opened the archive, validated its contents or changed a file. Its list is a convenience, not a promise that every archive is valid.

Read the controls

Get-Options converts the selected indices and checkboxes into engine parameters. The GUI checks that input scopes do not overlap. Start-Work disables editable settings, creates the worker and begins the preview.

Validate and plan

The engine validates the profile, scan scope and archive metadata. It reads each entry through a CRC/size/SHA-256 check. Flatten chooses the final filename. Get-LmsTarget decides whether that destination should be written, skipped, duplicated, renamed or overwritten.

Show the plan

For a new file, the Preview table shows a Write action and its destination. No PDF or extraction folder was created. Apply becomes available only after a successful preview with work to do.

Apply checks again

Apply starts a new engine call. It does not blindly execute old table rows. The engine rereads the archive and filesystem, stages verified bytes, then publishes the planned outputs. External edits made after preview can change the actual result.

Publish, then remove the ZIP

Each file is copied to a unique temporary file beside its destination and atomically moved/replaced. Once the archive’s planned publication completes, the archive is closed and deleted unless Keep ZIP is selected.

Report a real result

The dispatcher receives counts and details, stops progress, shows a persistent Done state and an Open result folder action. Apply is disabled until a fresh preview. Errors and cancellation have different messages.

“Atomic” is limited to one published file.The operation is not a database transaction across all outputs. If the third publication fails, the first two may remain and the ZIP is kept. The UI and documentation deliberately say this.
05 / CORE

The hard part is deciding what must never happen.

1. Contain every output path

A ZIP entry name is untrusted data. ../../outside.txt, absolute paths, empty components, reserved Windows names, control characters, trailing spaces/dots and alternate-stream syntax are rejected. Backslashes and forward slashes are normalized. The engine resolves a full destination and checks it starts with the chosen root plus a directory separator.

The separator matters: a naive prefix check could mistake C:\Courses-old for a child of C:\Courses. Assert-PlainPath also walks the target’s ancestors to reject symlinks and junctions. A safe-looking pathname alone cannot tell you where a link redirects writes.

2. Validate the archive before publication

ReadChecksums locates the ZIP end record, reads central-directory metadata (including ZIP64 metadata when needed), rejects split/encrypted/unsupported-method archives and returns CRC values in entry order. The engine checks entry counts, declared expanded bytes and entry types before processing file data.

CopyChecked uses an 81,920-byte buffer. It tracks actual expanded length, updates CRC-32 and SHA-256, and optionally writes bytes to a staging stream. An entry that exceeds its declared size fails immediately; an incorrect final size or CRC fails at the end. SHA-256 is returned only after validation succeeds.

CRC-32

“Does the decompressed content agree with this ZIP’s stored checksum?” Useful for corruption detection. It is not a digital signature.

SHA-256

“Does this content match another file?” Used for collisions and undo validation. A bare hash does not establish who published the file.

Authenticode

“Was this executable signed by this certificate?” A separate distribution mechanism. The current public builds are unsigned.

3. Plan before publishing

The archive routine first collects all planned entries. It rejects file-versus-directory collisions and any target that would replace an input archive. Apply stages data under a random temporary directory; Preview uses the same streaming validation with no output stream. Reading a large ZIP twice is deliberate: preview correctness and rechecking current data cost time.

4. Publish predictably

Install-LmsFile creates the target parent, copies verified staged bytes into a sibling .lms-write-GUID file, then uses Move or Replace. Replace-LmsFile retries bounded IOException failures because indexers or scanners may briefly hold a file. It never retries forever or discards the staged source before success.

5. Bound work and clean owned scratch

Defaults allow at most 10,000 entries and 2 GB declared expanded size per ZIP. These are configurable within validated ranges. Preview still spends CPU reading data. Apply needs storage for staging and publication. Streams are disposed in finally blocks; scratch cleanup only targets the application’s own generated directory. No generic recursive cleanup of the user’s course tree occurs.

Why not call Expand-Archive and delete the ZIP?

That would not implement the same guarantees: a shared preview plan, validated incoming content even for skipped files, per-entry hashes, collision decisions across several inputs, protected output targets and consistent structured details. A built-in extraction call can be useful in a small prototype, but it does not replace this policy layer.

06 / DECISIONS

Same filename does not mean same content.

Get-LmsTarget is a loop around a candidate destination. If it is unused, reserve it in PlannedTargets. If it exists or is already planned, compare hashes. Identical content becomes Duplicate. Different content follows Skip, Rename or explicit CLI Overwrite.

Try the decision yourself

This simulator only changes the example below; it cannot access your files.

Why a shared reservation table matters

Queue item A → lecture.pdf, hash AAA
Queue item B → lecture.pdf, hash BBB

Skip:   A reserves lecture.pdf; B is skipped.
Rename: A reserves lecture.pdf; B tries lecture_1.pdf, then _2, etc.
Same:   B is Duplicate if its bytes match the chosen candidate.

If each archive planned independently, both could claim the same unused filename during preview. Shared targets make the order visible before Apply. The engine copies the reservation map for each archive and merges it only when that archive succeeds, so a failed archive does not leave phantom reservations in the rest of the batch.

Rename checks numbered candidates too. If lecture_1.pdf already contains the incoming bytes, it can skip an identical duplicate instead of creating lecture_2.pdf. This is destination-based duplicate detection, not a library-wide search for identical content.

Loose-document organization is stricter: it never overwrites or removes the original on collision. Overwrite is rejected when organizing existing documents. Keep the distinction when extending conflict behavior.

07 / CLASSIFICATION

A syllabus becomes explicit rules, not guesses.

A profile is a small Version 1 JSON document with course mappings and ordered rules. Courses map codes to visible folder names. A rule matches a course and filename pattern, then supplies a category/week folder and optional topic/reason.

{
  "Version": 1,
  "Courses": [{ "Code": "BIO-101", "Folder": "Biology", "Name": "Biology I" }],
  "Rules": [{
    "Course": "BIO-101", "Pattern": "*cell*",
    "Folder": "Lectures/Week 02", "Topic": "Cell biology",
    "Reason": "Week 2 in my syllabus"
  }]
}
CourseMatch the ZIP’s code prefix or its containing course folder.
→
RuleFirst applicable filename rule wins; otherwise use built-in filename categories.
→
GroupingLectures become categories, known weeks, or named topics.

How matching works

Read-LmsRules validates fields, safe folder names and duplicate codes/folders. It compiles case-insensitive wildcard matchers once. Get-LmsCourse uses an escaped code prefix with a boundary; longer codes are checked first. A course code in the archive that conflicts with its containing mapped course folder is rejected rather than silently routed.

Get-LmsClassification caches the relevant rules per course, then tests them in order. For ordinary wildcard patterns it also normalizes repeated spaces, underscores and hyphens, helping common LMS naming variants. Patterns containing bracket character classes keep their original semantics.

When no custom rule matches

Get-LmsCategory recognizes terms such as assignment, homework, syllabus, quiz, exam, book, lab number, practice, week number and lecture. Submission/evidence-style names are protected from broad automatic guessing. A reliable “Week 02” LMS folder label can supply a week when a suitable filename has none.

GroupingWith a lecture ruleWithout the missing detail
CategoryLecturesA recognized lecture still goes into Lectures.
WeekLectures/Week 02 (or an explicitly supplied range)Lectures/Unscheduled
TopicLectures/Cell biologyLectures/Unsorted topics

Assignments, books and other categories stay separate. Unknown loose documents stay where they are. An unknown ZIP entry is extracted into the selected course/output root; it is counted as unclassified and explained in the preview. There is no automatic “Unclassified” destination folder in the current engine.

What the editor actually saves

The visual editor binds two DataTables to DataGrids. Saving serializes rows to a temporary JSON file, validates it using the engine, then copies it to a new destination without overwriting an existing profile. “Add rule for selected file” starts with an escaped exact filename and inserts that rule first. Users can deliberately widen it to a wildcard.

The CSV importer converts Code,Folder,Name and syllabus rows into the same JSON model. If a syllabus row supplies Week instead of Folder, it creates Lectures/Week NN. The example NUST profile is optional data, not hard-coded engine knowledge. The Calculus fixture is a list of example filenames and expectations, not private course documents.

08 / RECOVERY

Undo remembers moves, not a backup of everything.

Organizing an existing document uses File.Move. Before moving, the engine records its relative source, relative target, content hash and state in a JSON journal under the selected root’s .lms-unpacker/history.

PendingWrite the intended move to the journal first.
→
MovedMove the file, then persist the successful state.
→
RestoringDuring undo, record the return move before executing it.
→
UndoneThe original location has been restored and recorded.
{
  "Version": 1,
  "Root": "C:\\Courses",
  "Moves": [{
    "Source": "Biology/cell.pdf",
    "Target": "Biology/Lectures/Week 02/cell.pdf",
    "Hash": "SHA256_OF_THE_ORIGINAL_CONTENT",
    "State": "Moved"
  }]
}

The placeholder hash above is explanatory, not a valid journal to run. Real hashes are recorded from actual file content. Save-LmsJournal writes JSON to a temporary file and replaces the journal, reducing the risk of a half-written JSON document.

Why undo validates the entire plan first

A user may edit a file after organizing it or put another file in its original location. Undo checks the journal’s version, original location, containment, links, target existence and hashes before moving anything. It refuses occupied originals or modified files. It reverses the move order and recognizes recoverable Pending/Restoring states after interruptions.

The history dialog is an index, not the authority to restore files. It deduplicates locations, bounds record listing, rejects oversized/linked records and displays unavailable records honestly. The engine validates again when the user previews/applies undo.

Cancellation and undo are different.Cancellation asks the running operation to stop at a safe boundary. Completed work remains. Undo restores validated loose-file moves from a journal. Neither restores a permanently deleted ZIP or rolls back extracted/overwritten files.

Undo itself can encounter a filesystem failure after preflight, so it persists Restoring/Undone states as it progresses. Empty category directories are intentionally left in place. If several organization runs affected the same files, restore the most recent applicable run first.

XAML is the layout description

Desktop.xaml declares controls with stable x:Name identifiers. The startup script loads it through XamlReader and retrieves each named control with FindName. A missing control name stops startup with an explicit error. The $ui dictionary is the bridge between the markup and event handlers.

A Grid divides remaining space; Auto rows size to content, and star rows use remaining height. A StackPanel lays out controls in sequence. A ScrollViewer contains long settings so they remain reachable in a small window. The task heading now lives outside the scrolling content, preventing the partially cut-off heading seen in earlier layouts.

Why the interface changed in 1.4.1

  • The main header is smaller and removes a repeated tagline, returning vertical space to results.
  • The first settings tab shows the task, retention notice and collapsed extraction options. Workspaces/queue and Start menu setup no longer compete for that space.
  • Empty result areas explain the next useful action instead of showing only a blank table.
  • Apply is the single colored action; Preview remains a clearly labeled standard button.
  • Organization-only tools appear only when relevant. Conflict-comparison columns appear only when comparisons exist.

Why the tooltip was clipped

A tooltip containing a raw string is normally presented through a content presenter. Constraining the tooltip and setting an inherited TextBlock property did not reliably create the desired wrapping text layout. The fix supplies a ContentTemplate with an actual TextBlock, TextWrapping="Wrap" and a bounded width. Named-control popups explicitly receive the style because a popup has a separate visual tree.

<DataTemplate>
  <TextBlock Text="{Binding}" TextWrapping="Wrap" MaxWidth="340" />
</DataTemplate>

The template handles long prose and unbroken paths. Hover help also has an AutomationProperties.HelpText equivalent. Tests measure the actual popup layout, including a long path, instead of checking only that a tooltip string exists.

Accessibility choices

Labels point to inputs; underscore access keys provide Alt shortcuts; Tab and Shift+Tab follow normal control focus; buttons show keyboard focus; results have named accessibility roles; feedback uses polite live settings. System colors are retained in high-contrast mode instead of forcing the normal green palette.

Virtualized DataGrids avoid creating a visual row for every file at once. Detailed text can be selected and copied. Meaning is conveyed in words, not just green/red. Hover descriptions supplement the visible controls and visual guide. These choices help accessibility but do not substitute for acceptance testing by real screen-reader users.

The current UI architecture is intentionally direct

This is event-driven WPF with a shared state dictionary, not a full Model-View-ViewModel framework. DesktopFeatures.ps1, DesktopFeedback.ps1 and DesktopDiscovery.ps1 are dot-sourced into the UI scope. That keeps a small app approachable but makes shared dependencies less explicit. If the app grows, introduce a view-model boundary gradually while retaining the tested engine contract.

10 / RESPONSIVENESS

The UI thread must remain free to paint.

If a Click handler directly decompresses a large ZIP, the window cannot redraw or respond to Cancel. Start-Work creates a PowerShell runspace and invokes its script asynchronously. The worker owns the engine call; the UI timer owns visible updates.

A DispatcherTimer checks roughly every 180 ms. Read-Activity drains new information-stream messages without repeating old ones. Update-Feedback throttles more detailed text to roughly 500 ms, so progress stays useful without excessive layout work. When the async handle completes, the UI calls EndInvoke, inspects error streams, obtains the final result and disposes the worker.

What the progress percentage means

The bar measures completed entries in the current phase. Reading and publishing have different costs; the next archive resets counts. Unknown totals use indeterminate progress. The taskbar mirrors working, paused/cancelling, error and idle states. There is no fabricated whole-queue ETA.

What cancellation means in code

Cancel sets Control.CancelRequested. Entry reads and publication are allowed to finish at defined safe boundaries. The engine checks between entries and before archive publication; once publication begins, it finishes that archive’s planned publication before returning to a boundary. A successfully completed archive may already have been deleted. The UI refuses ordinary window closure while an operation is active.

Why discovery has a second worker

Typing a path should not queue a dozen filesystem scans. Discovery requests are debounced with a 300 ms timer. Each request has a version number; a stale worker result is discarded if a newer request exists. Discovery does not publish results during extraction, preventing it from stealing the user’s result view or racing the main UI state.

A small state machine to keep in your head
Ready → Previewing → Preview ready → Applying → Done
  ↑          ↓              ↓             ↓
settings   Error      settings changed   Error / Stopped
changed                 (invalidates)      ↓
  └──────────────── fresh preview ─────────┘

“Preview ready” is not “Done.” “Stopped” is not “Rolled back.” Error handling should preserve these distinctions in both button enablement and visible words.

Startup priority

  1. An explicit launch path wins.
  2. Otherwise look for nearby ZIPs beside the actual EXE, including one level of course folders.
  3. If no nearby ZIPs exist, try the remembered selection; retain the appropriate fallback when neither contains ZIPs.
  4. For source launches, use the working directory when there is no packaged EXE location.

Get-LmsLaunchFolder, Get-LmsPickerFolder and Get-LmsStartupSelection isolate these choices. The host supplies LMS_APP_EXE; it is a location signal, not a credential.

One level is a boundary, not “recurse everywhere”

Courses/
  general.zip                 found
  Calculus/
    downloads.zip             found at depth 1
    Week 02/deeper.zip         not found
  Lab/project.zip             protected child folder: not scanned

The shared scan helper is used by discovery and extraction. Known working/category folders, hidden folders and links are excluded from the child scan. Selecting a protected folder explicitly is different from automatically descending into it. Depth 0 restricts processing to the selected directory.

What is stored locally

%LOCALAPPDATA%\LMS Unpacker\preferences.json stores the last input, independent picker memories and named workspaces. A workspace stores paths, queue, task, profile selection/path, grouping, conflicts, retention and scan depth. It does not copy documents or embed the profile contents. Moving a custom profile can therefore require updating the workspace.

The optional installed copy lives at %LOCALAPPDATA%\Programs\LMS Unpacker. The Start shortcut points there, not at the random temporary runtime. Removing the shortcut does not delete the app copy or preferences. Keeping those responsibilities separate avoids surprising data loss.

12 / DISTRIBUTION

A single file can contain a modular application.

The source command path

Run-Unpack.sh / standalone CLI
        ↓
Start-Cli.ps1 → Start-Unpacker.ps1 (guided menu)
        ↓                  ↓
Unpack-Lms.ps1       shared engine directly
        ↓
Invoke-LmsUnpacker

The source BAT calls Start-Unpacker.ps1 directly for its guided menu. The direct script uses CmdletBinding, validated sets/ranges, ShouldProcess and compatibility switches. It converts -DryRun/-WhatIf into a real engine preview and expanded gigabytes into bytes. -PassThru returns the structured result. The CLI parser accepts an explicit allowlist of switches and value parameters, rejecting duplicate or unknown options.

No arguments starts the guided menu. That menu always previews before asking to apply. Named arguments execute directly, so the user should supply -DryRun when reviewing. Do not make these interfaces silently differ in destination rules or retention defaults.

The Windows EXE path

BuildExplicit runtime file list → App ZIP → embedded C# resource.
→
LaunchUnique temp folder → unpack own payload → start Windows PowerShell.
→
ExitWait for child → propagate exit code → remove owned temp folder.

PortableHost.cs is compiled twice with DESKTOP or CLI constants. The desktop build is a windowed executable and hides the child console; the CLI is a console executable. Both embed the same app ZIP. The manifest requests normal user privileges and declares Windows compatibility; it does not currently specify DPI awareness.

Arguments are serialized as JSON, UTF-8 encoded, then Base64 encoded into LMS_ARGUMENTS. The fixed child command starts a trusted embedded script; it does not splice user paths into PowerShell code. Base64 is transport encoding, not encryption or validation. The receiving script still validates the arguments.

The process-scoped execution policy does not permanently change account policy. Managed machines can still prohibit the program or dynamic compilation. A forced process kill may leave an owned temporary directory; the normal finally cleanup cannot run after a hard termination.

The Linux shell path

Build-Linux.ps1 packs the CLI runtime files into an in-memory ZIP and appends Base64 text after a marker in LinuxLauncher.sh. At launch, Bash checks for pwsh, creates a unique temporary directory, decodes the payload, calls the small PowerShell launcher and traps exit for cleanup. "$@" preserves separate arguments, including spaces.

PowerShell 7 is a prerequisite, not embedded. The Linux distribution does not pretend WPF is portable. It shares extraction, profiles and undo with Windows, while retaining conservative Windows-compatible filename restrictions. It does not restore Unix permission bits, links or special device files.

13 / WORKSHOP

Rebuild it in twelve achievable stages.

Keep your learning copy separate from real course materials. At each stage, make a tiny synthetic fixture and verify an observable behavior. The order below creates useful checkpoints rather than one enormous rewrite.

Create the engine boundary

Make a module with Invoke-LmsUnpacker returning an object containing counts, errors and details. Start with a read-only listing of files. Add a thin script that validates parameters and calls it. Success: both direct module and script calls produce the same result.

Add safe path construction

Implement relative-path normalization, disallowed components, containment and link checks. Write fixtures for ../escape.txt, rooted paths, reserved names and a junction parent. Success: every invalid target is rejected without creating outside files.

Read ZIPs with integrity checks

Use ZipArchive for entries and decompression. Implement or carefully reuse the C# checked-stream helper. Test correct ZIP, changed CRC, truncated data, empty ZIP and declared size limits. Success: even an incoming file that would later be skipped is checked for corruption.

Build a preview plan

For each entry, calculate a target and an action. Use a hash sink during Preview rather than extracting to disk. Success: a directory snapshot before/after preview is identical, including absence of new logs and undo directories.

Add conflict policy and publication

Implement a shared destination map; test two entries and two ZIPs targeting the same name. Add staging, sibling temporary writes and Move/Replace. Only delete the source ZIP after successful publication. Success: a publication failure preserves the ZIP, and the result explains partial work.

Add optional classification

Debug by following the contract

  • Wrong folder? Inspect classification Reason and Target first, then course matching and GroupBy. Do not start by changing XAML.
  • Apply disabled? Check preview completion, errors, cancellation and whether settings invalidated it.
  • ZIP not deleted? Check KeepZip, preview mode, errors and cancellation before assuming a delete bug.
  • App frozen? Check for engine or hashing work accidentally called on the UI thread, and for blocking event handlers.
  • Old discovery result? Inspect DiscoveryVersion and the worker’s active version.
  • Works from source, fails as EXE? Inspect the explicit build payload list and portable host environment. A missing helper script is a packaging bug.
  • Clipped popup? Inspect the popup’s actual content template and measured size, not only the owner control’s style.

Prefer tests that exercise these consequences over tests that simply repeat a private function’s implementation. Fixing a high-impact file operation deserves regression coverage. A wording change usually needs review rather than a new elaborate unit test.

Build artifacts are a product of verified source.

Local build

powershell.exe -NoProfile -File .\Build-Release.ps1

# Preview only known generated clutter:
powershell.exe -NoProfile -File .\tools\Clean-Workspace.ps1

The Windows build runs engine/desktop tests unless PackageOnly is selected, generates the icon, packages an explicit runtime list, compiles both hosts and runs standalone release checks. It refuses to overwrite an existing versioned ZIP. Stable EXE names are updated. Build-Linux requires PowerShell 7 and creates the shell file and checksum.

After a full build, dist should contain four deliverables and four SHA-256 sidecars: desktop EXE, CLI EXE, Linux shell and versioned modular ZIP. The modular ZIP is a runtime distribution; clone the repository for build tools and tests.

Continuous integration and release flow

Source / tagVersion tag must match VERSION.

The workflows grant jobs only the permissions they need. Ordinary tests use read access. The release build can issue attestations; the draft job can write releases. Actions are pinned to commits. Dependabot proposes action updates for review. A GitLab source mirror provides another repository location; it does not magically add a second independent security audit.

Signing is separate from provenance

Sign-Release.ps1 uses an existing code-signing certificate from the current user’s Windows store, checks validity/private key/code-signing usage, signs EXEs and refreshes hashes. It does not issue a certificate. An explicit testing flag permits an untrusted chain for private experiments; that does not create public trust.

Signing changes the executable bytes. Previous hashes and attestations no longer describe the changed file. If a signing service is integrated later, the release flow must attest and publish the final signed bytes. Current documentation describes unsigned builds and pending SignPath preparation without claiming approval.

What belongs in Git

Commit source, example profiles, tests, docs and workflow configuration. Ignore dist, test scratch, logs, private courses, downloaded documents, credentials and signing keys. Local agent notes are ignored at the maintainer’s request. The cleaner validates paths, rejects links, preserves unknown files and verifies current artifacts before removing older versioned packages.

A clean root is not an empty root: documented source entry points remain there so commands stay easy to run. Related material lives in docs, profiles, packaging, tests and tools. Moving every script into a new hierarchy would create packaging/import churn without automatically improving the user’s single-file download.

17 / JUDGMENT

Choices you can change—once you understand the cost.

Current choiceBenefitTradeoff / a reasonable next step
PowerShell + platform .NETSmall source and familiar Windows automation.5.1 compatibility and script-policy limits. A future compiled engine could keep the same public contract and tests.
Native WPF desktopOS controls, keyboard support, no browser runtime.Windows-only. A cross-platform GUI would need a deliberate toolkit choice and new accessibility tests.
Direct event handlers/shared UI stateApproachable small application.Coupling grows with features. Extract view models or controllers when the state graph becomes hard to reason about.
Depth 0 or 1Avoids unexpectedly touching projects and nested resources.Deeper ZIPs require explicit selection. If adding recursion, expose scope visibly and preserve exclusion/link handling.

Atomic per-file publicationNo half-copied final file on successful Move/Replace.No archive-wide rollback. A transactional design would need durable backup/recovery and more storage.
Destination-based duplicate checksFast, understandable conflict behavior.Does not deduplicate identical content under unrelated names. A content index would add persistence and invalidation complexity.
Single-file hostEasy sharing and installation.Startup temp extraction; runtime requires PowerShell. A native installer might improve updates but adds packaging/support obligations.
No auto-updaterNo network behavior in the app.Manual download/Start-copy replacement. A future updater needs trusted update metadata, rollback and explicit privacy documentation.

Useful extensions, in a sensible order

  1. Real screen-reader and high-DPI user testing, including long translated labels.
  2. Better rule editing: test a pattern against example filenames, show why one rule wins, and warn about shadowed rules.
  3. Queue convenience: visible per-input summaries and clearer handling of unavailable saved paths.
  4. Cross-process coordination for two instances pointed at the same output, with stale-lock recovery.
  5. Free-space checks that account for staging and destination volumes, while still handling race conditions at write time.
  6. A signed final-artifact pipeline after legitimate signing approval, with checksum/provenance tests covering those exact bytes.

These are proposals, not shipped claims. Every change should preserve the distinction between extraction, organization, preview, cancellation and undo. Avoid adding a network service or large dependency simply because it is fashionable; start with the concrete user problem.
